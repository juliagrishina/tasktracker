# Trello: REST-подключение и рабочий протокол

Этот документ — операционная инструкция для работы с доской **Task Tracker — Development**. Он описывает только безопасный REST-процесс и не содержит секретов.

## Источники истины

- Trello хранит оперативное состояние разработки: карточки, статусы, приоритеты, владельцев, Bug и Tech Debt.
- Notion — канонический источник постоянных правил разработки и рабочего протокола; этот файл синхронизирует правила, нужные для работы из репозитория.
- `docs/tz/` — источник продуктовых и архитектурных требований.
- GitHub/репозиторий — исходный код, документация и история изменений.
- `docs/TECH_DEBT.md` — только историческая точка сверки до переноса записей в Trello; параллельный бэклог в нём не поддерживать.
- Исторические документы не заменяют актуальные ТЗ из `docs/tz/`.

Работать разрешено только с доской **Task Tracker — Development** в workspace «Рабочее пространство Trello». Другие доски не читать и не изменять без отдельного запроса пользователя.

## Единственный способ подключения

Для этой доски используется только **Trello REST API** с API key и token со scope `read,write` и неистекающим сроком действия.

**Trello MCP/плагин не используется** ни для чтения, ни для записи. Он не поддерживает Custom Fields, поэтому создаёт риск неполных и несогласованных карточек. Подключение этого типа должно быть отключено в настройках приложения.

### Секреты и локальная конфигурация

- Требуются переменные `TRELLO_API_KEY` и `TRELLO_TOKEN`.
- Они живут только в локальном игнорируемом `.env`; секреты никогда не попадают в Git, документацию, Trello-карточки, чаты, логи или вывод команд.
- Не открывать и не выводить `.env` вручную: штатные REST-скрипты получают значения локально.
- Не печатать URL с query-параметрами `key`/`token`, заголовки авторизации и содержимое `.env`.
- В диагностике допустимы только безопасные сведения: операция, HTTP status, имя доски/карточки/списка и результаты read-back.

Перед любой изменяющей операцией выполнить безопасный REST GET: проверить, что доступна ровно одна целевая доска.

## Стандартный REST-процесс

1. Получить доступные доски и однозначно найти `Task Tracker — Development` по имени.
2. Получить открытые списки, карточки и Custom Fields этой доски.
3. Найти сущности по имени. Не хардкодить ID доски, списка, карточки, поля или option, если их можно получить из REST.
4. Перед созданием карточки проверить открытые и закрытые карточки нужного Epic/Type, определить следующий свободный номер и убедиться, что карточки с таким ID нет.
5. Создать или изменить карточку через REST JSON body. Для обновления списка и описания использовать JSON, а не form-encoded body.
6. Сразу заполнить все обязательные Custom Fields.
7. Выполнить обязательный read-back: повторным GET проверить название, список, описание и фактическое значение каждого Custom Field. HTTP 200 на запись сам по себе недостаточен.

Штатный помощник для обновления существующей карточки — [update-card.ps1](./update-card.ps1). Он:

- получает доску, список, карточку и поля по имени;
- обновляет список, описание и значения полей через REST;
- выполняет read-back каждого изменённого значения;
- выводит только безопасный итог операции.

При создании новой карточки сначала создать её REST-запросом, затем применить `update-card.ps1` для полей, списка/описания и read-back.

## Списки и переходы

| Список | Назначение |
| --- | --- |
| Backlog | Известная, но ещё не запланированная работа |
| Planned | Ближайшая работа, ещё не начатая |
| In Progress | Работа, которую исполнитель реально выполняет сейчас |
| Blocked / Deferred | Остановленная или сознательно отложенная работа |
| Review | Реализация завершена и ждёт ревью пользователя |
| Done | Подтверждённая пользователем завершённая работа |

Обычный путь: `Backlog → Planned → In Progress → Review → Done`.

- `In Progress → Blocked / Deferred` требует причины и условия возврата.
- `Review → Done` переводит только пользователь.
- При захвате карточки исполнитель устанавливает `Owner` на себя, переводит карточку в `In Progress` и проверяет оба изменения read-back.
- `Owner` — текущий исполнитель, а не автор идеи. В `Review` владелец сохраняется.

## Типы, ID и Custom Fields

### Типы и названия

- Task в эпике: `E{n}-T{n} — Название`.
- Bug в эпике: `E{n}-B{n} — Название`.
- Tech Debt в эпике: `E{n}-TD{n} — Название`.
- Работа вне эпика: `Bug {n} — Название` или `Tech Debt {n} — Название`.

Нумерация Task, Bug и Tech Debt ведётся отдельно внутри эпика. Удалённые и закрытые номера не переиспользуются. ID после создания не меняется.

### Обязательные поля

| Поле | Тип/значения | Правило |
| --- | --- | --- |
| Epic | text | Номер эпика, например `E5`; пусто для работы вне эпика |
| Type | dropdown | `Task`, `Bug`, `Tech Debt` |
| Priority | dropdown | `P0`, `P1`, `P2`, `P3` |
| Severity | dropdown | `Critical`, `High`, `Medium`, `Low` |
| Owner | dropdown | `Юля`, `Claude`, `Codex` |

`Priority` отвечает на вопрос «насколько скоро», `Severity` — «насколько серьёзны последствия»; их не смешивать.

Для Epic 05 при создании Tech Debt обязательно задать:

```text
Epic: E5
Type: Tech Debt
Priority: P2
Severity: Medium
Owner: Codex
```

Поле `Severity` заполняется для Bug и Tech Debt независимо от Priority. Critical и High могут сразу попасть в Planned только когда их нельзя устранить в текущем цикле; Medium и Low всегда идут в Backlog.

## Содержимое карточки

Каждая карточка должна быть самодостаточной и содержать:

- контекст и цель;
- конкретный scope;
- явно исключённый scope, если есть риск расползания;
- критерии готовности/приёмки;
- ссылки на релевантные `docs/tz/epic-XX-*.md` и код;
- для Bug: observed vs expected behavior, воспроизведение и известную причину;
- для Tech Debt: суть долга, почему он отложен и условие возврата;
- для Blocked / Deferred: причину остановки и условие разблокировки.

## Правила исполнения

### Task

Перед началом проверить acceptance criteria, затрагиваемые компоненты и актуальное ТЗ эпика. После реализации выполнить обязательные проверки проекта. Перед `Review` добавить completion report: что сделано, изменённые файлы/компоненты, проверки и их результаты, ограничения, связанные Bug/Tech Debt и конкретный checklist для ревью пользователя.

### Bug

Сначала воспроизвести проблему, зафиксировать observed/expected behavior и по возможности установить причину. После фикса запустить сценарий воспроизведения и релевантные regression-проверки.

### Tech Debt

До начала подтвердить, что долг актуален, и определить ожидаемый технический результат. Не расширять карточку массовым рефакторингом без согласования.

### Внешние проблемы

Проблема вне scope текущей карточки:

- блокирует работу — перевести текущую карточку в `Blocked / Deferred` с причиной и условием возврата;
- не блокирует — зарегистрировать отдельную Bug/Tech Debt-карточку, классифицировать её и продолжить текущую работу без opportunistic-исправления;
- Critical чинить сразу, High — в текущем цикле, если это разумно; Medium/Low не исправлять автоматически.

После 2–3 самостоятельных безуспешных циклов диагностики Critical/High остановиться, зафиксировать проверенные гипотезы и запросить решение пользователя.

## Проверка перед завершением

Перед отчётом убедиться, что:

- карточка находится в корректном списке;
- обязательные Custom Fields заполнены и подтверждены read-back;
- описание сохранено и самодостаточно;
- для `In Progress → Review` выполнены acceptance criteria и все обязательные проверки;
- карточка не переводится агентом в `Done`.

## Запреты

- Не использовать Trello MCP/плагин для этой доски.
- Не создавать карточку без обязательных Custom Fields.
- Не хранить, не логировать и не коммитить секреты.
- Не обращаться к другим доскам без явного запроса.
- Не принимать неоднозначные продуктовые, UX- или архитектурные решения вместо пользователя.
