# Реестр технического долга

Канонический временный реестр известного технического долга проекта — до подключения Trello или аналогичного трекера. Содержит только уже явно обнаруженные и сознательно отложенные пункты — не используется для планирования будущей функциональности (sync, multi-device, backup/restore, рекомендательная система и т.п. — это roadmap, не долг).

Epic 03 (планирование/scheduling) не входит в этот реестр — незавершённая бизнес-логика Epic 03 принадлежит отдельной ветке разработки (Codex ownership) и не является техническим долгом текущей кодовой базы.

## TD-001 — Запись `events` идёт в обход `AppDataSource`

- **Severity:** MEDIUM
- **Затронуто:** `src/application/backlog-use-cases.ts`, `src/application/convert-reminder-to-task.ts`, `src/data/events-client.ts`
- **В чём долг:** `recordEvent()` из `events-client.ts` напрямую импортирует `supabase-client.ts` и вызывается из application-слоя, минуя единую абстракцию `AppDataSource`. Application-слой перестал быть написан исключительно против `AppDataSource` — часть облачной логики не проходит через общую точку абстракции.
- **Почему отложено сейчас:** осознанное решение при внедрении Anonymous Auth/events на соответствующем этапе — минимальный объём инфраструктуры без введения новой абстракции (event sink), которая расширила бы scope того этапа.
- **Когда закрыть:** имеет смысл пересмотреть при проектировании `SupabaseDataSource`/полноценного sync-слоя — тогда естественно появится общая точка абстракции для облачных операций, через которую можно провести и запись событий.
- **Ссылка на канонический источник:** не зафиксировано отдельно в `docs/tz/` — решение задокументировано только в ходе финального code-only аудита текущей сессии.

## TD-002 — Повторный `UPDATE` на уже soft-deleted строках без `deleted_at IS NULL`

- **Severity:** LOW
- **Затронуто:** `src/data/data-source.native.ts`, `src/data/data-source.web.ts` (`deleteProject`, `deleteTaskItem`)
- **В чём долг:** вспомогательные `UPDATE`-запросы при каскадном откреплении/soft delete зависимых записей (открепление задач от удалённого проекта, soft delete подзадач) не проверяют `deleted_at IS NULL` перед записью — это лишний, но безвредный `updated_at`-шум на уже невидимых строках.
- **Почему отложено сейчас:** функционально безвредно — не влияет на видимое поведение приложения ни сейчас, ни при отсутствии sync.
- **Когда закрыть:** имеет смысл устранить вместе с реализацией настоящего sync-движка, когда «шумные» `updated_at` на невидимых строках станут значимы для разрешения конфликтов.
- **Ссылка на канонический источник:** `docs/tz/account-data-and-cloud-architecture.md`, раздел «Известный некритичный долг».

## TD-003 — Разные механизмы `transaction()` в native и web data source

- **Severity:** LOW
- **Затронуто:** `src/data/data-source.native.ts` (реальная SQL-транзакция через `withTransactionAsync`), `src/data/data-source.web.ts` (ручной snapshot/restore пяти `Map`)
- **В чём долг:** два принципиально разных механизма обеспечения атомарности между native и web реализациями `AppDataSource`.
- **Почему отложено сейчас:** это не следствие перехода на multi-user/облачную архитектуру — асимметрия существовала до текущей серии изменений. Оба механизма дают эквивалентную атомарность на своей платформе и не создают препятствий для будущих `user_id`/RLS/sync.
- **Требует ли это будущего исправления:** нет — это принятое архитектурное решение, а не дефект. Пункт включён в реестр как **наблюдение**, а не как задача с обязательным закрытием; можно пересмотреть только если появится конкретная причина унифицировать поведение (например, общий тестовый набор, требующий идентичной семантики отказа).
- **Ссылка на канонический источник:** не зафиксировано в `docs/tz/` — отмечено в ходе финального code-only аудита текущей сессии.

## TD-004 — Нет механизма удаления истории поведения (`events`) пользователем

- **Severity:** MEDIUM
- **Затронуто:** `src/data/events-client.ts`; таблица `public.events` в Supabase
- **В чём долг:** приложение уже собирает поведенческую историю пользователя (`events`), но не предоставляет ни UI, ни серверной операции для её удаления вместе с удалением аккаунта.
- **Почему отложено сейчас:** сознательное решение — детальная политика хранения (retention), согласие (consent) и связанные privacy-механизмы вынесены на будущий этап при актуализации ТЗ под multi-user модель.
- **Когда закрыть:** до публичного production-релиза с реальными пользователями — это явное условие, зафиксированное в каноническом документе, а не отложенная бессрочно задача.
- **Ссылка на канонический источник:** `docs/tz/account-data-and-cloud-architecture.md`, раздел «`events` — история поведения пользователя» (абзац «Приватность»).
