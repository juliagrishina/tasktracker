# Epic 07 — Техническая проверка Microsoft 365

**Приоритет:** nice-to-have, условный · **Порядок реализации:** 7 из 9

## Цель эпика

Проверить на реальном корпоративном контуре, можно ли безопасно подключить Microsoft 365 в рамках разрешений только на чтение календаря. Это не разработка пользовательской интеграции: результатом должен стать обоснованный вывод **go** или **no-go** для Epic 08.

## Пользовательские сценарии

- Как пользователь корпоративной учётной записи, я хочу понять, можно ли подключить мой календарь без предоставления прав на изменение данных.
- Как владелец продукта, я хочу принять решение об Outlook на основе реального успешного или заблокированного входа, чтобы не задерживать основной MVP.
- Как пользователь локального планировщика, я хочу продолжать пользоваться всеми основными функциями независимо от результата проверки Microsoft 365.

## Функциональные требования

1. Проверка должна выполняться только после готовности автономного ядра приложения; она не должна быть условием выпуска Epic 01–06.
2. Для проверки следует зарегистрировать или использовать согласованное публичное клиентское приложение Microsoft Entra ID без client secret в мобильном приложении.
3. Вход должен использовать системный браузер и OAuth 2.0 Authorization Code Flow с PKCE.
4. Набор запрашиваемых delegated permissions должен быть минимальным: `openid`, `profile`, `offline_access`, `User.Read` и `Calendars.Read`.
5. Разрешения на запись календаря, отправку почты, доступ к файлам, каталогу пользователей или административные разрешения не допускаются.
6. На реальном тестовом устройстве и корпоративной учётной записи необходимо проверить интерактивный вход, возврат в приложение, получение профиля и безопасный запрос чтения календаря.
7. Токены и сведения сессии должны храниться только в защищённом хранилище устройства и не должны выводиться в логи, аналитику, документацию или репозиторий.
8. Необходимо зафиксировать наблюдаемый результат: успешный вход, требование администраторского согласия, блокировка политикой, запрет tenant, недоступность тестовой учётной записи либо иной воспроизводимый барьер.
9. При положительном результате следует подтвердить, что необходимый read-only доступ работает и доступен путь к реализации Epic 08.
10. При отрицательном результате следует зафиксировать no-go, не реализовывать Epic 08 и не ухудшать локальное приложение.

## Критерии приёмки

- [ ] Создана краткая запись результата проверки с датой, используемым типом клиента, набором scopes и выводом go/no-go; секреты и токены в ней отсутствуют.
- [ ] В успешном случае реальная учётная запись проходит вход через системный браузер, возвращается в приложение и позволяет прочитать данные календаря с `Calendars.Read`.
- [ ] В успешном случае подтверждено отсутствие разрешений на запись и отсутствие операций записи в Microsoft Graph.
- [ ] В неуспешном случае причина зафиксирована достаточно конкретно для повторной проверки, а Epic 08 объявлен пропущенным.
- [ ] Независимо от исхода все функции Epic 01–06 остаются доступны без Microsoft 365.

## Зависимости от других эпиков

- Зависит от Epic 01: конфигурация приложения и безопасное хранение локального состояния.
- Может выполняться после завершения основного MVP; Epic 08 зависит от положительного результата этого эпика.
- Требует доступа к тестовой корпоративной учётной записи и, при необходимости, согласования с администратором Microsoft 365.

## Технические детали и ограничения

- Использовать системный браузер через Expo AuthSession или эквивалентный поддерживаемый механизм; не использовать встроенную webview для авторизации.
- Использовать `expo-secure-store` только для защищённого хранения токенов при успешном эксперименте.
- Проверка на реальном iPhone требует development build и, для распространения на устройство вне Expo Go, соответствующей инфраструктуры Apple; это не меняет работоспособность локального MVP.
- Не обходить корпоративные политики, MFA, ограничения tenant или требования администратора. Если они препятствуют входу, это корректный результат no-go.
