# Epic 05 — Уведомления и сценарии завершения

**Приоритет:** must-have · **Порядок реализации:** 5 из 9

## Цель эпика

Помочь пользователю вернуться к запланированному действию и принять явное решение по его результату. Эпик предотвращает бесконтрольное накопление просроченных дел, не вводя скрытых автоматических изменений.

## Пользовательские сценарии

- Как пользователь, я хочу получить напоминание до начала блока, чтобы вовремя перейти к делу.
- Как пользователь, я хочу после окончания последнего блока ответить, удалось ли закончить задачу, чтобы план отражал реальность.
- Как пользователь, я хочу перенести незавершённое дело или вернуть его в Backlog, чтобы самому решить, как поступить дальше.
- Как пользователь, я хочу получать вечернюю проверку незавершённых дел, чтобы закрывать день осознанно.

## Функциональные требования

1. Приложение должно запрашивать разрешение на локальные уведомления в контексте, понятном пользователю; отказ не должен блокировать работу приложения.
2. По умолчанию уведомление должно планироваться за 10 минут до начала собственного блока; значение берётся из настроек и может быть изменено в Epic 06.
3. После окончания последнего блока задачи или подзадачи приложение должно показать сценарий «Удалось закончить?» при следующем доступном взаимодействии с пользователем.
4. При положительном ответе элемент должен быть завершён, остаться в плане выбранного дня с признаком выполнения и одновременно появиться во вкладке «Завершённые».
5. После завершения приложение должно предложить создать связанное напоминание через 3, 7, 14 дней или через пользовательский срок; отказ от предложения должен быть возможен.
6. При отрицательном ответе пользователь должен выбрать одно из явных действий: продолжить, перенести на другое время или вернуть в Backlog; при возврате в Backlog причина может быть указана необязательно.
7. При выборе «Продолжить» приложение должно автоматически продлить на 30 минут последний связанный блок задачи или подзадачи; пользователь может отредактировать получившееся время. Для повторяющегося дела изменение применяется к выбранному экземпляру, если пользователь явно не подтвердил применение ко всей серии.
8. Вечерняя проверка должна показывать незавершённые на текущую дату дела и напоминания, не переводя их автоматически без выбора пользователя.
9. Повторяющиеся элементы должны обрабатываться по правилам отдельного экземпляра: завершение или перенос одного экземпляра не должны менять всю серию без подтверждения.
10. Уведомления должны пересчитываться при изменении времени, отмене, завершении или удалении связанного дела. Для повторяющейся серии приложение хранит конкретные локальные уведомления только в скользящем горизонте ближайших 90 дней, пересчитывает их при запуске приложения и при каждом изменении серии или экземпляра.
11. Завершённое дело можно возобновить: в редакторе — кнопкой «Возобновить», а в плане дня и «Завершённых» — из меню долгого нажатия. Пользователь может оставить размещение в плане, вернуть дело в Backlog или открыть планирование заново.
12. Для повторяющегося дела возобновление относится к выбранному экземпляру; действие над серией применяется только к будущим экземплярам и не изменяет явно завершённые прошлые экземпляры.
13. В MVP не должно быть фонового трекера времени, автоматического завершения по окончании блока или скрытого переноса задач.
14. Браузерный прототип должен позволять пройти сценарии разрешения на уведомления, завершения, переноса и вечерней проверки на тестовых состояниях без отправки реальных уведомлений.

### Уточнение: единое поведение одиночной задачи и одиночного напоминания

Одиночное напоминание в плане дня считается тем же типом пользовательского дела, что и задача без точного времени. Для обеих сущностей доступны одинаковые точки входа: обычное открытие редактора, контекстное меню по правому клику в браузере и long-press в мобильном приложении. В редакторе и быстром меню доступны «Выполнено», «Возобновить» для завершённого дела, «Вернуть в Backlog» и «Удалить»; у напоминания не показываются только действия, не имеющие смысла без блоков (например, создание временного блока через отдельное действие «Запланировать»).

«Вернуть в Backlog» для одиночного напоминания выполняется атомарно: снимает статус завершения, очищает дату и период (`remindsOn`, `periodStartOn`, `periodEndOn`) и удаляет связанную серию повторения. Напоминание сохраняется как активный элемент Backlog и не остаётся в плане дня. Это правило одинаково применяется из плана дня и из раздела «Завершённые».

## Критерии приёмки

- [ ] При выданном разрешении создаётся уведомление за настроенное количество минут до блока.
- [ ] При отказе от уведомлений пользователь всё равно может создавать, планировать и завершать дела.
- [ ] После последнего блока доступны понятные варианты завершения и незавершения; состояние не меняется до выбора пользователя.
- [ ] Завершённый элемент остаётся в плане выбранного дня в сером зачёркнутом состоянии, появляется в «Завершённых», учитывается в загрузке дня, а уведомления для него отменяются.
- [ ] «Продолжить» автоматически продлевает последний связанный блок на 30 минут (например, 12:00–13:00 превращается в 12:00–13:30) и позволяет отредактировать результат; «Вернуть в Backlog» убирает запланированные блоки.
- [ ] Вечерняя проверка не завершает и не переносит элементы автоматически.
- [ ] Изменение одного повторяющегося экземпляра соблюдает выбор области применения.
- [ ] Возобновление из редактора и меню долгого нажатия возвращает дело в активное состояние без потери явно выбранного пользователем размещения; возврат в Backlog снимает размещение.
- [ ] Для повторений конкретные уведомления созданы только в горизонте 90 дней, а после изменения экземпляра или серии устаревшие уведомления отменены.
- [ ] Через `npm run web` доступны интерактивные варианты диалогов и их результаты для ключевых сценариев эпика.

## Технические детали и ограничения

- Использовать `expo-notifications`; уведомления должны быть локальными и не зависеть от backend.
- В базе необходимо хранить связь между делом, блоком или экземпляром повторения и идентификатором запланированного уведомления, чтобы корректно отменять и пересоздавать его в 90-дневном горизонте.
- Поведение после пропущенного уведомления не должно предполагать, что пользователь увидел сообщение.
- Браузерный прототип моделирует состояния уведомлений и не отправляет push или локальные уведомления.
- Тексты и системные разрешения должны быть совместимы с требованиями iOS.

## Приёмочные состояния web-демо

При запуске через `npm run web` демо-данные создают состояния для текущей даты в часовом поясе плана:

- в «Настройках» можно пройти выдачу или отказ в разрешении на уведомления без отправки реального уведомления;
- в «Плане» есть завершившийся повторяющийся блок, из которого доступны сценарии завершения, незавершённого дела и связанного напоминания;
- в «Плане» есть незавершённые безвременные задача и напоминание для ручного открытия вечерней проверки.

Эти состояния предназначены только для демонстрации и приёмочной проверки: они не выполняют скрытых действий с планом и не эмулируют отправку нативных уведомлений.
