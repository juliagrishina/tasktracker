# Epic 09 — Качество, доступность и подготовка релиза

**Приоритет:** must-have · **Порядок реализации:** 9 из 9

## Цель эпика

Подтвердить, что планировщик стабильно работает как ежедневное офлайн-приложение на iPhone и понятен пользователям с разными системными настройками. Эпик объединяет техническую проверку, доступность и подготовку сборки к распространению без расширения функционального объёма MVP.

## Пользовательские сценарии

- Как пользователь, я хочу пользоваться планировщиком без интернета, чтобы данные и основные действия были доступны в любой ситуации.
- Как пользователь, я хочу, чтобы текст был читаемым при увеличенном системном размере, а элементы были доступны VoiceOver, чтобы приложение не исключало меня из работы.
- Как пользователь, я хочу, чтобы даты и расписание не ломались на границе дня, месяца и часового пояса, чтобы доверять плану.
- Как владелец продукта, я хочу установить проверенную сборку на iPhone, чтобы провести финальное тестирование и распространение.

## Функциональные требования

1. Основная пользовательская функциональность Epic 01–06 должна работать без интернет-соединения после установки приложения. Фоновые best-effort сетевые операции (анонимная идентификация в Supabase, отправка событий поведения — см. [«Аккаунт, данные и облачная архитектура»](account-data-and-cloud-architecture.md)) допустимы, но не должны блокировать, замедлять или нарушать эту функциональность при отсутствии сети.
2. Необходимо покрыть автоматическими тестами доменные правила: структуру сущностей, планирование, конфликты, повторения, расчёт загрузки, сценарии завершения и архивирование.
3. Целевое покрытие критичной доменной логики должно быть не ниже 80%; процент не заменяет проверку ключевых сценариев.
4. Необходимо выполнить ручную проверку на реальном iPhone с актуальной поддерживаемой версией iOS.
5. Интерфейс должен поддерживать Dynamic Type, VoiceOver, светлую и тёмную тему, а интерактивные зоны должны быть не меньше 44×44 pt там, где это применимо.
6. Следует уважать системные настройки уменьшения движения и прозрачности, не полагаясь только на цвет для передачи важного смысла.
7. Необходимо проверить даты, время и повторения на границах суток, месяца, года, високосного дня и при смене временной зоны устройства.
8. Необходимо проверить удаление, перезапуск приложения, повторное открытие локальной базы и отсутствие потери несвязанных данных при редактировании сущностей.
9. Должны быть подготовлены воспроизводимые инструкции сборки Expo development build и, при наличии необходимой учётной записи Apple, путь к TestFlight/EAS Build.
10. Отсутствие Apple Developer Program не должно блокировать локальную разработку и проверку через Expo Go там, где это технически возможно; ограничения такого режима должны быть зафиксированы.
11. Если Epic 08 включён, дополнительно должны быть проверены read-only права, безопасное хранение токенов, отключение учётной записи и сохранность локальных данных при ошибках Outlook.
12. В релиз не должны попадать секреты, токены, персональные тестовые данные, отладочные журналы авторизации или неиспользуемые функции записи в Microsoft Graph.
13. Каждый завершённый эпик должен сохранять доступный браузерный прототип, запускаемый командой `npm run web`; этот путь включается в регрессионную проверку MVP.

## Критерии приёмки

- [ ] Автоматические тесты критичной доменной логики проходят, а измеренное покрытие составляет не менее 80%.
- [ ] Полный путь «создать → запланировать → получить проверку результата → завершить/перенести → найти в архиве» успешно проверен на устройстве.
- [ ] Приложение запускается и выполняет основные сценарии в авиарежиме.
- [ ] Ручные проверки на краях календаря и при смене часового пояса не выявляют некорректных дат, дубликатов или потери блоков.
- [ ] Ключевые экраны корректно работают с увеличенным текстом, VoiceOver, светлой и тёмной темой.
- [ ] Сборка устанавливается на тестовый iPhone выбранным доступным способом; известные ограничения распространения задокументированы.
- [ ] Если Outlook включён, подтверждены только операции чтения и отсутствие утечки токенов; если Epic 07 дал no-go, отсутствие Outlook не считается дефектом MVP.
- [ ] `npm run web` успешно запускает интерактивный браузерный прототип, а его ключевые пользовательские пути проходят регрессионную проверку.

## Зависимости от других эпиков

- Зависит от Epic 01–06 как от обязательной функциональной основы.
- Зависит от Epic 08 только если ветка Microsoft 365 реализована после результата go в Epic 07.
- Является финальным эпиком для приёмки и подготовки поставки.

## Технические детали и ограничения

- Использовать TypeScript strict, линтеры и тестовую инфраструктуру, совместимую с React Native/Expo.
- Прогонять проверки миграций SQLite и сценариев повторения на фиксированных часовых поясах, чтобы тесты были воспроизводимыми.
- Для TestFlight потребуется участие в Apple Developer Program; до этого можно использовать Expo Go для базовой проверки и development build на доступных условиях, но эти способы имеют ограничения для нативных модулей и распространения.
- Браузерный прототип служит для согласования и регрессии общих экранов, но не заменяет нативную проверку SQLite, уведомлений, доступности iOS, безопасного хранилища и Microsoft 365.
- Не добавлять в рамках этого эпика новые продуктовые возможности: его задача — подтвердить качество согласованного MVP.
