## Что изменилось с момента, когда Codex остановился

- Проект теперь исходит из multi-user архитектуры, а не single-user/local-only.
- Подключён Supabase.
- Anonymous Auth включён и используется как identity с первого запуска.
- Существуют `profiles` и `events`.
- RLS защищает пользовательские данные.
- `CompletedItem`/`completed_items` удалён; завершённость хранится через `completedAt`.
- Добавлены `updatedAt`/`deletedAt`, пользовательское удаление переведено на soft delete.
- Локальная модель подготовлена к будущей синхронизации.
- Исправлены связанные триггеры/каскады и проверка soft-deleted родителей.
- `saveRecurrenceSeries` теперь валидирует существование активной задачи.
- Epic 03 в рамках hardening-сессии не продолжался и его бизнес-логика намеренно не менялась.

## Что Codex категорически не должен возвращать назад

- Не возвращать hard delete для пользовательских бизнес-сущностей.
- Не возвращать `CompletedItem`/`completed_items`.
- Не исходить из модели «один пользователь / только локальные данные / аккаунтов нет».
- Не убирать `updatedAt`/`deletedAt`.
- Не обходить новые правила soft delete и проверки активных родителей.
- Не переписывать новую архитектуру под старые формулировки Epic 03.

## Границы ownership Epic 03

- Продолжать только незавершённую бизнес-логику планирования/scheduling Epic 03.
- Не реализовывать sync engine, `SupabaseDataSource`, multi-device, backup/restore, постоянный аккаунт, рекомендательную систему и другие будущие эпики.
- Если код Epic 03 конфликтует с текущей архитектурой `main`, адаптировать Epic 03 к новой архитектуре, а не откатывать общую архитектуру проекта.

## Правила работы из-за ограниченных лимитов

- Сначала читать актуальное ТЗ и текущий код, не проводить повторный полный архитектурный ресёрч без необходимости.
- Не запускать субагентов/параллельные исследования без явной необходимости.
- Не закапываться в бесконечный bug-fixing.
- Найденные проблемы классифицировать как CRITICAL / HIGH / MEDIUM / LOW.
- В рамках Epic 03 автоматически исправлять только CRITICAL/HIGH, если они действительно блокируют или ломают текущую реализацию.
- MEDIUM/LOW не расширять в отдельную работу: фиксировать в `docs/TECH_DEBT.md`, если это техдолг, и продолжать Epic 03.
- Перед крупным изменением сначала показывать план и затрагиваемые файлы.
